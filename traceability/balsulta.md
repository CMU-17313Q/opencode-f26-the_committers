# Traceability: Mistake parser for /mistakes (balsulta)

Target feature: the mistake parser, [student-error-parser.ts](../packages/core/src/session/student-error-parser.ts), which reads compiler and test output and records each mistake for `/mistakes`.

Property tests: [student-error-parser.property.test.ts](../packages/opencode/test/student-error/student-error-parser.property.test.ts). They live in `packages/opencode` because that is where the team added fast-check (PR #33); they import the parser from `@opencode-ai/core`. Run them with `cd packages/opencode && bun test test/student-error/`.

Evidence IDs: S- lines are from the real staff interview. C- and O- lines are from simulated classmate and outside interviews, written with instructor permission (see the P4A workbook).

## Requirement changes

| ID  | Original (P4A)                                                                                                  | Revised (P4B)                                                                                                                                       | Why it changed                                                                                                                                                                                                                                                                                                             |
| --- | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R2  | A test that fails and then passes on a retry in the same output is not recorded as a failure.                   | If a test's failed line is followed later in the same output by a passed line for the same test name, that failure is not recorded.                 | Checkability and feasibility. The parser only sees the text of one command's output, so it cannot know that a run "was a retry". What users needed (S-4, O-4) was not to be blamed for a test that passed in the end. The revised wording says exactly what the parser can see: a later pass line with the same test name. |
| R5  | Parsing two outputs joined together gives the first output's mistakes followed by the second's.                 | Same, as long as the second output does not report a pass for a test that failed in the first.                                                      | Conflict with R2. If A contains `(fail) x` and B contains `(pass) x`, R2 says the joined output records no failure for `x`, but the original R5 says it must record parse(A)'s failure. Users wanted both (S-9: joining is predictable; S-4: retried tests are not blamed), so R5 now excludes exactly the case R2 covers. |
| R8  | The number of recorded mistakes equals the number of compiler error lines plus failed-test lines in the output. | The number of recorded mistakes equals the number of compiler error lines plus failed-test lines whose test does not pass later in the same output. | Conflict with R2. A failed test that later passes would count under the original R8 but must not be recorded under R2. Interviewees wanted a one-to-one count they can check against the terminal (C-10, O-10), so the count now matches what R2 says should be recorded.                                                  |

R1, R3, R4, R6 and R7 were kept as written: each is something the parser can do from the output text alone, does not conflict with another requirement, and has acceptance criteria a test can check.

## Generators

- **File paths**: relative paths, nested folders, Windows drive-letter paths (`C:\project\`, from O-7), and folders with parentheses like `src/(group)/`, which look like the `(line,col)` part of an error.
- **Line and column**: small numbers and very large ones (up to 99999).
- **Error codes**: every code the parser categorizes specially (TS1xxx, TS2304, TS2552, TS2307) plus random TS codes, so every category is reached.
- **Messages**: words with quotes, numbers and punctuation, like real compiler messages. They never start or end with spaces, because the parser trims lines.
- **Test names**: half from a small pool (so retries happen), half random, including brackets.
- **Noise**: the lines interviewees said should never count (C-3, C-4): `Compiling...`, `12 pass`, `Found 0 errors.`, blank lines, passing tests, and prose.
- **Color codes**: inserted at random positions in a line, like colored `tsc` output.
